# 景区导览服务 AI 数字人系统演示与答辩脚本

## 1. PPT 建议结构

1. 项目背景：景区讲解人力有限、游客咨询分散、路线推荐缺乏个性化。
2. 需求分析：游客端多模态交互、智能问答、个性路线；管理端知识库、数字人配置、游客反馈和数据大屏。
3. 总体方案：游客端、管理端、后端 API、本地景区知识库、SQLite 数据存储、多模态大模型 API。
4. 核心 AI：DashScope `qwen3-vl-plus` 作为多模态核心模型，支持文字问答和图片识别讲解。
5. 准确率保障：本地知识库 + RAG 检索 + 标准测试集 + 规则兜底。
6. 产品展示：AI 问答、语音播报、图片识别、GPS 附近景点、景点导览、路线推荐、管理后台、数据大屏。
7. 自然度方案：原创小僧童 2D 数字人形象、豆包语音、讲解状态动效和后续 TTS/数字人 SDK 升级。
8. 复杂场景：GPS 弱信号、室内定位、图片辅助定位、弱网兜底。
9. 团队分工：需求设计、前端、后端、AI 方案、测试与文档。
10. 后续规划：向量检索、TTS/ASR、Live2D/数字人 SDK、权限管理和真实景区数据接入。

## 3. 答辩讲解要点

### 3.1 功能完整度

系统覆盖 A5 要求中的游客文本/语音交互、数字人播报、景区问答、图片识别讲解、个性化推荐、知识库管理、数字人配置、游客感受报告和数据大屏。

### 3.2 多模态大模型

系统默认使用阿里云百炼 DashScope `qwen3-vl-plus` API，走 OpenAI 兼容接口。该模型既用于普通文字问答，也用于游客上传景区照片后的图片识别和讲解生成，满足“至少 1 个多模态大模型作为核心 AI 能力”的要求。

### 3.3 准确率保障

系统不是直接让模型自由回答，而是先检索本地景区知识库，再把景点资料、票务交通、安全服务和路线信息作为上下文传给模型。提示词明确要求不编造未入库事实。若 API 不可用或资料不足，系统切换本地规则兜底，并提示游客咨询服务中心或查看公告。

### 3.4 自然度保障

当前演示版使用原创“小僧童”2D PNG 形象，视觉上结合灵山胜境的莲花、念珠、青绿僧袍和导览耳麦。语音合成优先使用豆包/火山引擎 TTS，未配置时回退浏览器自然中文语音；播报时通过状态光效和音量条提示讲解中。后续可接入 ParaTTS、Whisper/faster-whisper、Live2D、SadTalker、MuseTalk 或 2D 数字人 SDK 进一步提升自然度。

### 3.5 稳定性与延迟

普通语音问答目标控制在 5 秒以内。系统设置模型调用超时，超时后自动使用本地知识库和规则回答，避免页面长时间无响应。常见问题会优先通过本地知识库稳定回答。

### 3.6 行业实用性

景区可通过后台持续维护景点、讲解词、票务交通信息和常见问题。游客咨询与反馈沉淀为热门问题、偏好分布和负向情绪线索，帮助景区优化导览内容和现场服务。

## 4. 推荐现场演示问题

1. 景区几点开放？
2. 停车场在哪里？
3. 适合亲子游的景点有哪些？
4. 哪里适合拍照打卡？
5. 如果我喜欢历史文化，应该怎么逛？
6. 灵山大佛手印有什么含义？
7. 身体不舒服应该去哪里？
8. GPS 定位不准怎么办？

## 5. 风险与兜底

1. 如果大模型 API Key 未配置，系统会展示配置缺失提示，文字问答可走本地规则兜底。
2. 如果图片识别失败，继续演示文字问答、路线推荐、知识库管理和数据大屏。
3. 如果语音输入不可用，改用文本输入，不影响核心演示。
4. 如果浏览器语音播报无声音，检查系统音量或改用 Edge/Chrome。
5. 如果数据演示不够丰富，可提前多提几个问题、多生成几条路线并点击反馈。
6. 如果数据库数据被改乱，删除 `backend/data/scenic_guide.db` 后重启即可恢复初始数据。
